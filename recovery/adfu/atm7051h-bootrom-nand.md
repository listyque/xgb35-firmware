# ATM7051H BootROM — загрузка MBREC из NAND

Ручная декомпиляция NAND-ветки. Имена функций восстановлены по поведению. Псевдокод описывает управление и адреса из дампа, а аппаратные операции оставляет вызовами функций ROM.

Разбор сделан по `atm7051h-high-rom-ffff0000-ffff7fff.bin`, ARM little-endian, база `0xFFFF0000`, размер `0x8000`. SHA-256 `e83e5ac0d25025a7eb948a796636bc7ff11a7a94f6904d1508434034a094757c`.

## Поиск загрузочного сектора

Адрес дескриптора основного чтения `0xB4068400`, дескриптора короткой адресации `0xB406840C`. В каждом `u16` по `+0` — колонка, `u16` по `+2` и `u8` по `+4` — младшие 16 и старшие 8 бит строки, указатель по `+8` — куда читать. Это видно в `0xFFFF302C`. У обоих дескрипторов колонка изначально 0, а назначение `0xB4068000`.

```c
// Диспетчер 0xFFFF2A00: nand(op, r0, r2, r3) помещает op в r1.
// Зависимые от аппаратного состояния ветки сохраняются.
int probe_nand(int init_arg) {                  // 0xFFFF118C
    d = d_short = { .column = 0, .row = 0, .dst = 0xB4068000 };
    nand(1, init_arg);                         // 0xFFFF2D88
    nand(2, 2);                                // 0xFFFF2CCC, поле CE = 2 << 3
    nand(7);                                   // 0xFFFF2D1C, NAND RESET FFh
    nand(15, _, 2, 8192);                       // 0xB4068446 = 8192
    nand(15, _, 1, 2);                          // 0xB4068444 = 2

    if (probe_geometry()) return 0;             // Строка 0, 0xFFFF1368
    if (probe_geometry_with_ctl_mode_2()) return 0; // Строка 0, 0xFFFF1684
    if (try_read_op12()) return 0;               // Строка 0, 0xFFFF156C
    if (try_read_op10()) return 0;               // Строка 0, 0xFFFF1520

    // Таблица в 0xFFFF16F8 хранится в обратном порядке.
    for (row : [32, 64, 128, 192, 256, 384, 512, 768, 1024]) {
        d.row = d_short.row = row;
        if (probe_geometry() || try_read_op10()) return 0;
    }

    // 0xFFFF15D8: меняет контроллер в режим 2 и делает NAND RESET.
    // Повторяет эти девять строк только через probe_geometry().
    // При неудаче восстанавливает режим 0 и снова делает NAND RESET.
    if (probe_table_with_ctl_mode_2()) return 0;

    if (nand(14) == 0) {
        for (row : [256, 512, 768, 1024]) {
            d.row = row;
            if (try_read_op12()) return 0;
        }
    }
    nand(3);
    nand(9);
    return -1;
}

bool probe_geometry() {                        // 0xFFFF1368
    for (size : [8192, 16384, 2048]) {
        nand(15, _, 2, size);
        if (nand(14) == 0 && try_read(4, &d, 0)) return true;
        if (try_read(4, &d, 1)) return true;
        if (try_read(4, &d, 3)) return true;
    }
    if (nand(14) != 0) return false;
    set_ecc_profile(0);
    if (d_short.address_halfword_at_4 >= 128) return false;
    nand(5, &d_short);
    return validate() == 0;
}

bool try_read(int op, desc *d, int profile) {
    set_ecc_profile(profile);                   // 0xB0320008, биты [1:0]
    nand(op, d);
    return validate() == 0;
}

bool try_read_op12() {                          // 0xFFFF156C
    nand(15, _, 2, 8192);
    return try_read(12, &d, 3);
}

bool try_read_op10() {                          // 0xFFFF1520
    nand(7);
    nand(10, &d);
    return validate() == 0;
}
```

В обоих проходах по таблице `1024` — последняя реально проверяемая строка. Значение `2048` на позиции 0 загружается в дескрипторы, а следующая проверка индекса выводит код из цикла до чтения (`0xFFFF12D8`, `0xFFFF1648`). Низкоуровневая короткая адресация в операции 5 программирует регистры иначе, чем операция 4. Числа в таблице выше — значения поля строки в дескрипторе.

## Чтение и передача управления

| Операция диспетчера | Адрес | Что видно в коде |
|---|---|---|
| 4 | `0xFFFF3598` | `00h/30h`, затем `05h/E0h`, настройка ECC и DMA. При флагах первого поиска профиль 0 задаёт 512 байт данных, профили 1 и 3 — 1024 байта. |
| 5 | `0xFFFF3844` | Короткий вариант адреса и чтение 512 байт. |
| 10 | `0xFFFF3C18` | Альтернативный путь чтения 512 байт после `RESET`. |
| 12 | `0xFFFF3968` | Вариант чтения с префиксом `A2h`. |
| 14 | `0xFFFF30D8` | Возвращает `(NAND_CTL >> 12) & 3`. |

```c
int validate(void) {                            // 0xFFFF2B9C, вызов через op 6
    const uint32_t *p = (const uint32_t *)0xB4068000;
    if (p[125] != 0x42746341 || p[126] != 0x55AA6D72) return 1;
    uint32_t sum = 0x1234;
    for (unsigned i = 0; i < 127; ++i) sum += p[i];
    return sum == p[127] ? 0 : 1;
}

// В общей процедуре загрузки 0xFFFF1000, после успешного поиска:
// 0xFFFF10E4: LDR r0, =0xB4068000
// 0xFFFF10E8: BLX r0
```

Даже когда контроллер переносит 1024 байта, валидатор смотрит первые 512. Режим ADFU по перемычке идёт с `0xFFFF09C0` сразу к вызову USB из `0xFFFF01C4`, минуя общую загрузку. NAND-ветка BootROM не разбирает `update.zip` и не ищет заголовок U-Boot. После `BLX` следующие чтения выполняет MBREC. В NAND-ветке MBREC берёт начальную строку из `0xB0320018`, вызывает операцию 4 и проверяет два фрагмента в SRAM (`0xB4068A00`, длина `0x400`, и `0xB4068E00`, длина `0x600`) перед переходом на `0xB4068E00`.

## Сверка с дампом этой приставки

В дампе 256 физических страниц на блок. Строка `0` — начало блока 0, строка `256` — начало блока 1. После снятия скремблирования обе строки содержат одинаковый валидный сектор MBREC с суммой `0xE15D8859`. Следующие два проверяемых MBREC фрагмента тоже сошлись в обеих копиях. В OOB строк `0`, `32`, `64`, `256` начало `FF BB 80 00`. Строки `512` и `768` начинают блоки U-Boot, у них OOB начинается `FF CC 90 00`. Наличие маркера в OOB само по себе не означает, что сектор проходит валидатор.

В предыдущем тесте вызов NAND-поиска из уже работающего ADFU оставил USB без ответа до чтения результата из SRAM. Поэтому выбранный в реальной загрузке режим ECC, результат чтения и факт перехода на MBREC остаются неизвестны. NAND в ходе этого разбора не трогалась.

## Проверка RAM-службой, 2026-11-16

Диагностическая сборка `autonomous-service-diagnostic` запускается после холодного старта одним исполнением BootROM, сама инициализирует DDR и поднимает USB. Проверены 64 обмена по 4096 байт и десять проверок с паузами. В ней команда исполнения возвращается в USB-цикл без штатного сброса USB: переход `0xB4069EFC -> 0xB406A440`, тестовый код в DDR `0x01000000`. `service_exec_probe.py` подтвердил исполнение по nonce и возврат без переподключения.

`service_nand_rom_probe.py` скопировала NAND init и read из ROM в RAM, сохранив USB PLL, и добавила четыре метки ожиданий. Чтение завершилось, все четыре ожидания вернули 0, USB остался доступен. Но без скремблирования результат — повторяющийся `E0`, а не NAND. С аппаратным скремблированием результат равен `E0 XOR заводская маска` на всех 1024 байтах. Это подтверждает маску, но НЕ правильность чтения NAND и НЕ успешную коррекцию ECC. Явная установка NAND_CTL `0x21` результата не изменила. Прямое чтение регистров после восстановления/выключения тактирования зависло: регистры надо сохранять внутри payload до отключения тактирования.

`verify_boot_ecc.py` проверяет формат по сохранённым дампам без доступа к устройству. На страницах 0–3 и 256–259 сошлись все 64 ECC: на 1024 байта данных идут 4 байта метаданных и 42 байта проверочного кода, восемь записей в OOB, затем 376 байт FF. Полином степени 336 и порядок битов сохранены в `nand-read-validation/ecc-verification.json`. Маска восстанавливается по первым 22 известным байтам каждого сектора: для 16-битных слов `w[n]=w[n-2]^w[n-3]^w[n-10]^w[n-11]`. Общая формула seed для произвольной строки ещё не получена.

Семь физических страниц воспроизводятся побайтно. В дампе страницы 259 один бит отличается: байт 2375, XOR `0x80`; её сохранённый ECC совпадает с исходным восстановленным MBREC. Причина битового расхождения (ячейка или чтение) не установлена, аппаратное исправление пока не проверено.

Для контрольного прямого чтения создана `service_nand_raw_probe.py`: только NAND RESET FF и READ 00/30, FIFO, ограниченные ожидания, восстановление тактирования. Первый запуск с NANDCLK=1 без PLL завис. После холодного старта вариант с NANDCLK=`0x21` завершился, но вся страница была заполнена `30`. Рабочая пара из старого дампера: `0xB015000C=0x210A`, пауза 2048 итерации, `0xB015004C=1`. Перед тестом PLL был `2`. С этой парой прямое чтение совпало с дампом полностью; та же настройка исправила штатный ROM reader. Оба скрипта сохраняют и восстанавливают исходные PLL/clock. Никаких изменений DDR PLL для этого не нужно.

В одном сеансе без перезапусков считаны восемь физических страниц 0–3, 256–259 и 64 ECC-сектора. Все сырые страницы совпали с дампом побайтно; все декодированные сектора совпали с восстановленным MBREC. На строке 259, секторе 2 сохраняется тот же битовый дефект сырого чтения, ROM возвращает правильный сектор, регистр ECC `0xB032003C=1`. Это подтверждает исправление одного реального ошибочного бита, но не предел корректирующей способности. Результаты находятся в `nand-read-validation/raw-row*.json` и `rom-flags2-row*-sector*.json`.

`service_nand_reader_probe.py` берёт реальные 280 байт reader из логического кандидата. Меняет только размещение в DDR, адреса буфера/дескриптора/guard, ожидаемую сумму заводских данных и адреса выхода в RAM-обёртку. Сам цикл с вызовами ROM, переходами страниц и cache maintenance остаётся прежним. Пройдены чтение 28 секторов (28672 байта) из обеих копий и ветка отказа с намеренно неверной суммой. Настоящий выход в BootROM ADFU и исполнение reader по исходному SRAM-адресу этим не проверяются.

`build_service_nand_pages.py` на ПК сформировала два физических кандидата по четыре страницы (35744 байта каждый) с рассчитанными ECC и масками конкретных строк. Все заводские 4-байтные метаданные и свободная область OOB сохранены. Обратное декодирование даёт логический кандидат, остаток каждого ECC-кодового слова равен нулю. Файлы `UNFLASHED-physical-rows-0-3.bin`, `UNFLASHED-physical-rows-256-259.bin` и подробный `physical-pages-manifest.json` лежат в `autonomous-service-nand-candidate`. Это не образы целых erase-блоков и не готовый план прошивки.

Никаких PROGRAM/ERASE и записи NAND не выполнялось. Текущий USB-сервис остаётся в RAM. Не проверены исходное SRAM-размещение reader/relocation, полная цепочка включения из NAND и native ADFU fallback. Нужен также план сохранения остальных страниц erase-блоков и резервных загрузочных копий; `flash_ready=false` сохраняется. Формат и чтение проверены на существующих заводских данных, новые страницы на устройство не передавались.

## Полная RAM-цепочка и аварийный ADFU, последующий тест 2026-11-16

`ram_chain_probe.py` успешно исполнила заводскую первую ступень по `0xB4068000`, ступень переноса по `0xB4068E00`, reader по `0xB4068200`, его штатную проверку суммы, инициализацию PMIC/DDR и запуск USB-службы по штатным SRAM-адресам. Перед исполнением DDR PLL был `0xA`. Отчёт DDR содержит `(0x41555431,3,0,0)`; восемь циклов записи/чтения DDR через USB прошли. Это заменяет прежний пункт о непроверенном SRAM-размещении и переходах.

Для этого теста два вызова NAND dispatcher были заменены RAM-провайдером по `0xB4068500`; суммы изменённых служебных ступеней пересчитаны. Полезная часть осталась неизменной. Три первых чтения подают заводские метаданные и ступень переноса; при первом запросе полезной части провайдер разворачивает весь образ в SRAM из сжатого источника. Остальные вызовы проверяют адреса и возвращают уже подготовленные данные. Счётчик подтвердил 31 чтение и последнее назначение `0xB406F400`. Проверена невозможность перезаписи ещё не прочитого сжатого источника. Поэтому тест покрывает исполнение/размещение/суммы, но не заменяет физическое чтение нового образа NAND при включении. Настоящий цикл NAND с ECC уже проверен отдельно на заводском содержимом.

Испытанные аварии:

- Неверная геометрия (`r5=0`) в неизменённом reader по настоящему SRAM-адресу: штатный переход `0xFFFF4A00`, IDENT и чтение памяти BootROM работают.
- Повреждённая сумма метаданных первой ступени: отказ после трёх чтений, возврат в ROM ADFU, nonce из SRAM совпал.
- Повреждённая полезная часть: отказ после 31 чтения, возврат в ROM ADFU, nonce из SRAM совпал.

Возврат из уже запущенной USB-службы требует дополнительной подготовки. Прямой переход и вариант с восстановлением только обработчиков/стеков USB не вернули. Рабочая `service_return_to_rom.py` также сбрасывает бит `0x40000` регистра `0xB0200000`, выполняет барьеры/сброс I-cache, восстанавливает семь маршрутов исключений и шесть banked SP из исходного ROM. Перед восстановлением регистр отображения был `0x50204`, обработчик IRQ — `0xB4068C50`. После этого ROM ADFU вернулся, IDENT, nonce и чтение `0xFFFF4A00` проверены. Утилита использует команды действующей службы; это не доказательство восстановления из произвольного зависания CPU.

Итоги: `nand-read-validation/ram-chain-validation.json`, отдельные `ram-chain-*-result.json`, `native-adfu-fallback-cold1.json`, `service-return-to-rom.json`. Полезный образ кандидата SHA-256 `2a95894f0d51f0002fad4945f6f7c34a24f6158a32f91069c41eb8d3e97f7333` не менялся. Физические кандидаты страниц не переписывались. На завершение тестов устройство находится в ROM ADFU, переход выполнен программно. NAND не записывалась и не стиралась. Остаются реальный старт BootROM из NAND с новым образом, план работы с erase-блоками/резервными копиями и отдельная проверка восстановления после произвольного зависания.

## Подготовка записи и восстановления, последующая проверка 2026-11-16

Проверена маркировка на фото: Micron `29F64G08CBABA WP:B`; ранее считанный ID `2c64444ba9000000`. Геометрия подтверждена документацией Micron Rev. E 11/11 и дампами: 8192+744 байта на страницу, 256 страниц на erase-блок. Полный сырой блок занимает 2287616 байт. Маркер плохого блока — первый OOB-байт первой страницы; в проверенных снимках блоков 0 и 1 он FF. Документация и конкретные ограничения сохранены ссылкой в `nand-write-preparation/RECOVERY-PLAN.txt`.

Дважды заново считаны все 512 страниц блоков 0 и 1 с OOB. Каждое чтение заняло около 16,7 секунды. Они сверены с двумя историческими источниками. Затем через диагностическую RAM-службу считаны с аппаратной ECC все 960 секторов 120 заполненных страниц. Каждое восстановленное кодовое слово независимо проверено относительно всех четырёх сырых снимков с восстановленной маской скремблирования. `nand_backup_format.py` проверяет также исправление ошибок в первых словах маски, в метаданных и в ECC. Поддержка восстановления метаданных ограничена одним повреждённым битом и останавливается при неоднозначности; это не общий BCH-декодер.

В исправленных образах относительно первого свежего снимка исправлен 41 бит в защищённых данных/метаданных/ECC; каждый записан в `corrections-vs-live-raw.json`. Пример: строка 105, сектор 3 содержит ошибку в ECC; строка 357, сектор 2 — бит в метаданных. Декодированные полные блоки 0 и 1 после коррекции совпадают. Не защищённый ECC хвост OOB сохранён побайтно из первого свежего снимка, включая постоянные не-FF биты; его расхождения не объявляются исправленными и перечислены отдельно. Все исходные чтения сохранены неизменными.

В плане первой записи разрешаемый диапазон только блок 0 (строки 0–255). Логическая замена занимает страницы 0–3. Образ `block0-candidate-REVIEW-ONLY.bin` содержит полный блок; страницы 4–255 совпадают с исправленным оригиналом. Подготовлен порядок 60 заполненных страниц по возрастанию, 196 пустых остаются без программирования. В первой записи блок 1 (256–511) и все блоки начиная с 2 не меняются. Файл `block0-restore-ECC-corrected.bin` предназначен для обсуждения отката в тот же блок 0; `block0-original-raw.bin` сохраняет точное исходное чтение с его ошибками. Исправленный блок 1 сохранён отдельно как резервное свидетельство, не как цель записи.

Сохранённая копия в блоке 1 не означает автоматический failover после принятого заголовка блока 0: ROM прекращает поиск, передав управление валидному первому сектору. Ошибки следующих ступеней в проверенных случаях ведут в ADFU, зависания могут потребовать аппаратного входа. Возврат старого MBREC не доказывает исправность нынешнего SYSTEM.

`prepare_nand_write.py` работает исключительно с локальными файлами, не содержит USB/PROGRAM/ERASE API. Она выпускает `write-plan.json`, пошаговый `RECOVERY-PLAN.txt`, полные образы и `nand-boot-recovery.zip`; архив проверяется по CRC и SHA-256 каждого файла. Архив содержит также старый дамп первых 32 МиБ с OOB, тестовые средства, доказательства проверок и зависимости Capstone. Это не полный дамп NAND объёмом 8 ГиБ. SHA-256 самого архива хранится в `recovery-archive.sha256`.

Запись и стирание NAND не выполнялись. План блоков и резервирования подготовлен; до фактической записи остаются проверенный PROGRAM/ERASE backend, копия архива на другом физическом носителе и свежая проверка ID/маркеров/бэкапа. Разрешения на саму запись пока нет. Последнее аппаратное состояние после ECC-проверок — диагностическая USB-служба в RAM.

Проверка аппаратного DMA в летучий буфер страницы 0 выполнена через `adfu_nand_cache_dma_probe.py`. В `NAND+0x0C` длина 8936 читалась обратно как 744, а 4096 как 0. Оба запуска оставляли DMA активным до тайм-аута. Для аппаратного писателя нельзя брать размер одной транзакции из прежнего теста с копией регистров в DDR.

Рабочая проба использовала `80h` один раз, затем девять фаз `85h` с DMA (`8 × 1024 + 744` байта), затем `FFh`. У каждой фазы проверены длина, адрес источника и переход DMA из активного состояния в завершённое. После сброса полный физический снимок страницы 0 с OOB совпал с исходным. Блок 1 не адресовался. Содержимое летучего буфера отдельно не считывалось. Программирование и стирание массива по-прежнему не проверены. Журнал сохранён в `nand-write-preparation/adfu-nand-cache-dma-probe.json`.

В последующем тесте `--read-cache` после девяти фаз DMA команда `05h/E0h` переключила чип на выдачу данных с колонки 0. До `FFh` FIFO считал 8936 байт, которые побайтно совпали с переданным кандидатом, включая OOB. Кандидат отличался от содержимого физической страницы 0 в 3040 байтах. После `FFh` страница 0 из массива снова совпала со снимком до теста. Команды подтверждения записи и стирания не подавались, блок 1 не адресовался. Журнал и данные буфера сохранены в `nand-write-preparation/adfu-nand-cache-readback.json` и `adfu-nand-cache-readback.bin`.

### Скрипт записи блока 0

`adfu_write_nand_block0.py` по умолчанию работает в режиме `plan`. Он сверяет ZIP и SHA-256 образов и собирает код команд для всех 60 страниц. `inspect` читает и сохраняет сырой блок 0 с OOB. Только явные режимы `write` и `rollback` с параметрами `--execute-block0 <SHA-256 целевого образа>` и `--expect-current <SHA-256 снимка inspect>` имеют доступ к стиранию. Они используют один эксклюзивный USB-дескриптор. Восстанавливаемый образ берётся из проверенного архива.

Перед `write` оба чтения сверяются с исправленным заводским образом. Допускается до двух отличающихся битов на кодовое слово ECC, а пустые страницы, маркер плохого блока и незашищённый хвост OOB сверяются точно. В свежем снимке оказалось 11 отличающихся битов относительно исправленного образа, все укладываются в этот предел. Для `rollback` требуется точное совпадение с проверенным снимком `inspect`, поскольку блок после прерванной записи может содержать неполные кодовые слова.

После стирания проверяется весь блок. Для каждой страницы код сравнивает весь летучий буфер с исходником на самой приставке и отправляет `FFh` при несовпадении. При совпадении повторный `85h` переводит чип в режим ввода перед `10h`. Затем проверяются статус NAND и физическое чтение страницы с OOB. В конце перечитывается весь блок. Журнал фиксирует начало каждой операции до её запуска и все подтверждённые чтения. При сбое операция останавливается. Для отката сначала `inspect`, затем отдельно `rollback` со снимком текущего блока. При неизвестном статусе после подтверждения нужно сначала убедиться, что операция завершилась. Блок 1 не адресуется ни чтением, ни записью из этого скрипта.

Проверены сборка, переход в `FFh` при несовпадении, последовательность записи и отката на модели, отказы при неверном статусе и контрольном чтении. На приставке проверен только `inspect`. Переход от сверенного буфера к `10h`, стирание, настоящий статус записи и физический откат ещё не проверены.

### Диагностика пустой страницы после `10h`

Первый аппаратный запуск стёр блок 0, подтвердил все 256 пустых страниц и остановился после первой попытки записи. RAM-отчёт показал сверенный буфер и статус `0xE0`, но весь блок при повторном чтении по-прежнему содержал `FFh`. Приставка оставалась в RAM-службе. Доказательства сохранены в `nand-write-preparation/block0-after-failed-write-state.json` и журнале записи. Дальнейшие проверки массива выполнялись только чтением блока 0.

`adfu_nand_rearm_probe.py` проверила четыре варианта на странице 0. Все тесты загрузили страницу бэкапа в летучий буфер и подтвердили побайтное чтение. После `05h/E0h` двухадресная форма `85h` с DMA не изменила тестовые байты OOB, хотя DMA завершился. Пятиадресная форма `85h` с тем же DMA изменила ровно восемь байтов OOB. При повторной подаче исходных восьми байтов вся страница осталась побайтно равна бэкапу. Каждый тест закончился `FFh`, физическая страница осталась пустой. `70h` без `10h` тоже вернул `0xE0`. Журнал `nand-write-preparation/adfu-nand-rearm-probe.json`. См. описание `CHANGE ROW ADDRESS` и `PROGRAM PAGE` в документации Micron, стр. 85 и 100.

Путь в скрипте исправлен: после сверки буфера он переводит NAND в режим ввода пятиадресным `85h` и повторно передаёт последние восемь уже сверенных байтов OOB. После будущего подтверждения он потребует наблюдать R/B# в busy, затем ready, проверит статус и физические данные. При откате полностью пустого блока по свежему точному снимку дополнительное стирание пропускается. Форсированный запуск без признака busy не предусмотрен. Сам переход через `10h` с исправлением и физический откат пока не запускались. Измерение R/B# подтверждено на части коротких `FFh`, пульс `tPROG` ещё не наблюдался.

### Обычное включение после восстановления блока 0

Откат заводского блока 0 завершился проверкой всех страниц с OOB. По наблюдению пользователя при обычном включении экран остался чёрным и USB-устройство не появилось. IDENT BootROM ADFU, `DDR PLL = 0xA`, слово `0x10031111` по адресу `0xB406FF90` и содержимое областей `0xB4068A00` и `0xB4068E00` сняты после отдельного ручного входа в ADFU. Эти значения не позволяют установить, до какой стадии дошёл предшествующий обычный запуск или откуда пришло слово в SRAM. См. `nand-write-preparation/block0-first-boot-usb.json`.

Парная проверка первого сектора строк 0 и 256 через одну и ту же подпрограмму чтения ROM из RAM показала разницу между режимами тактирования. При `NAND_CLK=0x21` и исходном `NAND_PLL=2` обе копии возвращают неверные данные. При `NAND_CLK=1` и временном `NAND_PLL=0x210A` обе копии читаются и совпадают с заводским MBREC. Оба результата получены внутри диагностической службы после ручного входа в ADFU. Для причины остановки при обычном включении это пока гипотеза. Настройки восстанавливаются после чтения. См. `nand-write-preparation/block0-first-boot-clock-test.json`. NAND в этом тесте не менялась.
